## 数据结构与保存

应用 2.1.0；IDB 整数版本 2；共用 schema 和 backup 版本 2.0.0。Shoe 按任务冻结的十个字段保存，`shoe_id` 为 UUID v4。一条记录的 `shoe_id` 为 null 或一双鞋 ID；不存鞋名快照、不做自动推断。目标业务字段及训练标签不变。

鞋子品牌/型号/昵称在手工保存时清理首尾空白；同鞋款昵称比较忽略大小写和首尾空白，包括退役鞋。自动建议编号计入全部历史鞋，人工输入优先。导入按 ID 保留同名实体；已导入的同名实体可以继续编辑备注/状态，未改变原名称组合时不强制改名，创建或改名不能引入新昵称冲突。

鞋子编辑/退役/恢复保留 ID 和创建时间，更新时间严格递增。没有硬删除鞋接口或 UI。历史记录始终引用 ID，按当前鞋名动态展示。退役默认隐藏于快速选择，已选退役鞋仍可见，也可显式显示并补录。记录与目标/鞋子引用在同一事务里验证。

## 原子迁移与异常恢复

0→2 创建四个 stores 和原索引；1→2 保留三个原 stores、创建 shoes，先验证旧目标，再用 cursor 验证及转换旧记录，目标仅技术版本升级，最后写元信息。所有请求均在 versionchange 事务内，没有外部 I/O 或清空数据动作。

迁移不刷新训练或目标的原更新时间；用鞋全部补 null。任何请求/校验失败显式 abort，版本、store 创建和已写记录一起撤销。界面报告升级失败和保留原数据/外部备份的恢复路径，不自动删库重建。旧窗口阻挡时显示中文提示，关闭后继续；收到 blocking 时关闭自身连接并要求刷新。

正式部署前必须在原 V2.0.1 主屏幕 PWA 导出 v1 JSON 到应用网站存储之外，确认文件可打开；不要公开真实备份。失败时保留现有数据库和外部备份，停止升级并等待兼容修复；如必须恢复，通过独立验证和人工授权进行受控恢复。

**IDB 2 不能直接交给 V2.0.1 的 `openDB(..., 1)` 使用，会得到 VersionError。旧 tag 只是代码锚点。** 不能靠部署旧代码、卸载 PWA、清理 Safari 或删除数据库实现安全回退。应使用兼容 IDB 2 的修复版本，或依据升级前外部 v1 备份受控恢复。

## JSON 与 CSV 边界

v1 和 v2 各自使用完整精确字段校验；混合版本、额外/缺失字段、错误 ID、枚举、日期、重复 ID 或缺失引用整份拒绝。v1 通过校验后才显式转换为内部 v2；其来源 envelope 保留到合并入口，避免来源语义丢失。新导出只生成 v2，含全部在用和退役鞋，旧应用不保证读取。

预览不写库，分别列出记录/目标/鞋子新增、更新、跳过和错误。实际导入在三 store 读写事务内重新计算，随后批量写入变更项；失败回滚整批。按 ID 比较实际更新时间，同时间保留本地。不同 UUID 的同品牌/型号/昵称鞋不合并。

较新的 v1 同 ID 记录可更新其它旧字段，但保留本地非空用鞋，并在预览/完成提示保护数量。v2 的 null 才能按正常更新时间规则明确清空用鞋。备份非空鞋引用必须存在于同份备份，不能借本地鞋补足不完整文件。

CSV 保留原 20 列及顺序、BOM、转义，仅追加用鞋 ID/品牌/型号/昵称/中文类型；空用鞋五列空白，未填鞋型为空，不追加动态退役状态。JSON/CSV 仍以设备本地时间命名，JSON 文件名和 exported_at 使用同一个 Date。

## 三个关键设计决定（通俗说明）

1. **认一双鞋的 ID，不认鞋名。** 两双完全同款也可能同时存在；改名或退役不会把以前的跑步指向另一双鞋。导入同名鞋不会擅自合并。
2. **升级要么全成，要么全撤销。** 不让手机出现“记录改了一半、鞋库却没建好”的状态，原时间和备注也不被技术升级改写。
3. **旧备份没有鞋字段，不等于用户说没穿这双鞋。** 因此保留旧文件来源并保护已补录用鞋；新版显式 null 才能清空。这样可继续用旧备份恢复其它信息。
