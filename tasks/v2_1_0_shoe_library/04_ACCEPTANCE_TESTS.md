# 04 — 验收与发布安全门槛

以下检查分为自动化（Codex 本机执行）与用户真机验收（发布后执行）；不得将尚未执行的真机项目标为 PASS。

## A. 数据结构与迁移（自动化必须）

- [ ] 新建空库 `oldVersion=0 → 2`：4 stores 正确创建，数据库正常打开，初始鞋库为空。
- [ ] 存量库 `oldVersion=1 → 2`：迁移全部合成旧记录、合成目标；逐一比对原 ID、时间戳、备注、RPE、训练标签和目标关联字节/语义不变，新记录鞋 ID 为 null。
- [ ] 一次模拟迁移中途失败：事务 abort，不能产生部分迁移。旧多标签页阻塞升级时给出既有中文提示。
- [ ] 新鞋可创建、编辑、退役、恢复，ID 不变；同型号多双鞋 ID 不同；防止鞋款内重复昵称，合法情况可新建。
- [ ] `shoe_id` 非 null 必须引用库中鞋，退役鞋也合法；无鞋 `null` 合法，非法引用拒绝。
- [ ] 新建/编辑记录保留所有原有业务字段与目标关联，编辑用鞋不改变 `record_id`、`created_at`。

## B. 备份、导入与合并（自动化必须）

- [ ] 原格式 v1 备份可被新程序严格验证并转换；旧记录补 `shoe_id=null`，旧目标与记录 ID 和时间戳保持。
- [ ] v2 JSON 导出含 `shoes`（在用与退役）+ `records` + `goals`；内部引用存在且有效；导出后在空 v2 库恢复，数量和内容均与导出前一致。
- [ ] v1 备份与 v2 本地同 ID 冲突：本地已有鞋引用**不会被旧格式的缺失鞋字段抹掉**；其他字段按照已定 `updated_at` 规则处理。
- [ ] v2 数据同 ID 更新时间比较遵守原有 merge 规则；相同时间保留本地；重复导入同一备份不生成重复记录/鞋。
- [ ] 缺少所引用鞋 ID、重复 ID、非法枚举、错误版本、损坏 JSON 均在真正写入之前报告，保证整批拒绝、不留下半导入状态。
- [ ] 导入预览新增鞋库 counts，并在真正导入时事务内重新计算；预览后本地数据变化仍一致。
- [ ] 相同品牌、型号和昵称但不同 UUID 的鞋**不能被静默自动合并**。
- [ ] CSV 维持旧列与次序，在末尾追加 5 个用鞋列；未填写为空，已关联信息正确；BOM、逗号/引号/换行转义正确。
- [ ] JSON/CSV 文件名时间戳继续可用，导出结构变化不破坏本地时间逻辑。

## C. UI/E2E（自动化必须）

- [ ] 鞋库空状态：未填写可保存记录；可以就地创建鞋，创建成功自动选中且原草稿不丢失。
- [ ] 两双同型号不同昵称的鞋同时出现在选择器，可分别选中并在历史详情查看准确的实体标签。
- [ ] 已退役鞋默认不打扰新记录；编辑旧记录时可显示并补选退役鞋；退役不会抹去既有引用。
- [ ] 补录旧记录、重新编辑、清空用鞋选择、刷新后状态均正确。
- [ ] 320px / 390px 屏幕：按钮、弹窗和长鞋名可见可点，没有水平溢出或不可关闭弹窗。
- [ ] 原有目标管理、记录 CRUD、帮助正文正常字重、删除二次确认滚动/焦点、RPE、JSON/CSV、离线能力不回归。

## D. 完整执行命令/报告（自动化必须）

- [ ] TypeScript typecheck
- [ ] ESLint
- [ ] 单元测试（包括迁移、导入、同 ID 保护）
- [ ] Chromium + WebKit 浏览器测试（包括移动视口）
- [ ] 生产 build + Service Worker 语法/离线检查
- [ ] `git diff --check`
- [ ] 最终 diff 无无关修改、仓库无真实个人训练数据或非预期二进制文件
- [ ] Codex 报告分清「已自动测试通过」「需要用户真机验证」；说明升级后旧版不可直接打开新版 DB 的限制

## E. 用户 iPhone 真机验收（部署后）

**生产部署前**：在现有主屏幕 PWA 导出 V2.0.1 的 JSON 到外部文件位置，核对文件存在且能打开。不要为测试删除正式数据。

- [ ] 从主屏幕打开新版应用，原有跑步记录和目标仍在，原字段/备注未丢失。
- [ ] 能在手机新增两双同型号的鞋、给旧记录选择其中一双、保存并再次打开核实。
- [ ] 对其中一双执行退役，历史关联保留；仍可显示已退役鞋以补录旧记录。
- [ ] 飞行模式下关闭再重新打开 PWA，仍可查看鞋库与旧记录；离线创建/编辑后本地保留。
- [ ] 导出新版 JSON 至手机文件 App，检查 `shoes` 与用鞋关联，留一份新版备份。
- [ ] 记录旧式 JSON 导入恢复能力只在**独立测试数据库**或合成样本中验证，不在唯一的真实库上冒险覆盖。

## F. 发布/回退门槛

- 先在特性分支完成全部自动测试和 diff 审查，随后人工授权合并 `main`，再手动触发从 `main` 的 GitHub Pages 部署。环境 branch rule 继续只允许 `main`。
- 新部署采用相同正式 URL，不卸载重装 iPhone PWA、不清理 Safari 网站数据。
- 真实 iPhone 检查通过后方可打 `v2.1.0` tag；有阻断错误则暂停 tag。
- **重要**：一旦用户真实数据库已升级为 IDB 2，简单重新部署 V2.0.1（IDB 1）不能恢复可用；必须使用兼容 IDB 2 的修复版本，不能通过清空库“回滚”。
